01 Case study

Rebuilding a production pipeline to break it properly

At TCS I worked on NSS DigitalTwinx, which loads millions of parcel records a day from terminals in Sweden. I didn't own the infrastructure or the failure handling there, so I rebuilt a smaller version in my own AWS account and ran 8 deliberate failure experiments on it. For each one I wrote down the symptom, how I diagnosed it, the fix, and how I'd prevent it in production.

view repo ↗
EXTRACTS3 rawdate-partitioned CSVs + carryover
GUARDHash ledgerskip files already ingested, by content
TRANSFORMPySpark · EC2dedup → validate → quarantine → enrich
LOADS3 + RDSParquet, MySQL delete+insert by batch_id
OBSERVECloudWatch8 metrics · 6 alarms · SNS email
  • Allow-list validation. Keep the rows you expect. Don't just filter out the ones you don't.
  • Idempotent loads. Delete-then-insert by batch makes any re-run safe.
  • Quarantine, not reject. Rows with an unknown terminal are kept aside instead of deleted.
  • Three layers of dedup. Spark, a MySQL UNIQUE KEY, and the file ledger. A bug has to get past all three to cause damage.
  • Batch cap with carryover. Volume spikes get queued for the next run, not crammed into this one.
  • Dirty data by design. The data generator injects 10 kinds of mess: stuck scanners, bad encodings, impossible weights.
FAILURE 01
silent data loss
exit code: 0
logs: clean
rows lost: ~0.5% / run

I swapped one allow-list filter for a block-list. The pipeline still finished, logged COMPLETED, and showed no errors, but every run quietly dropped some rows.

# looks harmless
col("action_type") != "ERROR"

# but in Spark / SQL
NULL != "ERROR"  → NULL → row dropped, never counted

I found it with a reconciliation check: raw = loaded + rejected + quarantined. The counts didn't add up. The fix was to go back to an allow-list with isin() and backfill the affected dates.

The bugs that worry me most are the ones that don't crash.
