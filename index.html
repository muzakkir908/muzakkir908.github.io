02 · Case study

I rebuilt a production
pipeline, then broke it
8 times on purpose.

At TCS I worked on NSS DigitalTwinx, which loads millions of parcel scans a day from terminals in Sweden. I didn't own the infrastructure or the failure handling there, so I rebuilt a smaller version in my own AWS account and ran 8 deliberate failure experiments on it: symptom, diagnosis, fix and prevention for each.

01 · ExtractS3 rawdate-partitioned CSVs + carryover
02 · GuardHash ledgerskip files already ingested, by content
03 · TransformPySpark on EC2dedup → validate → quarantine → enrich
04 · LoadS3 + RDSParquet, idempotent MySQL load
05 · ObserveCloudWatch8 metrics · 6 alarms · SNS email
Failure 01exit code 0 · logs clean · ~0.5% rows lost per run
# looks harmless
col("action_type") != "ERROR"

# but in Spark / SQL
NULL != "ERROR"   → NULL → row silently dropped

# the fix: keep what you expect
col("action_type").isin(["collection", "distribution"])

Found with a reconciliation check, raw = loaded + rejected + quarantined, then backfilled the affected dates.

  • Allow-lists, not block-listsKeep the rows you expect, and count everything else.
  • Idempotent loadsDelete-then-insert by batch, so any re-run is safe.
  • Three layers of dedupSpark, a MySQL UNIQUE KEY and a content-hash ledger.
  • Quarantine, don't deleteUnknown terminals are kept aside for review.
  • Batch cap + carryoverA 5× volume spike gets queued, not crammed in.
  • Dirty data by designThe generator injects 10 kinds of real-world mess.

07 · How I work

Four rules I don't break

01

Validate what you keep

Allow-lists over block-lists. Every row is loaded, rejected or quarantined, and the counts must add up.

02

Make re-runs boring

Idempotent loads and file ledgers, so a 3am rerun can't duplicate anything.

03

Alarm on the quiet failures

Metrics for rows lost and data freshness, not just job crashes. Exit code 0 isn't proof.

04

Write it down

Runbooks, failure logs and READMEs, so the next person fixes it in minutes, not days.
